How it is put together

Batchwell is a standard Frappe app with one governing idea: every rule lives in a document event, never in a screen. A rule that only runs in the console is not a rule — it is a suggestion that the Desk, the REST API and a Data Import all ignore.

Four layers, each allowed to call only downwards:

LayerResponsibility
FrontendVue 3 + frappe-ui at /fm. Presentation and nothing else; it holds no rule of its own.
api/Whitelisted HTTP surface. Checks permission, parses arguments, calls the domain, shapes the response.
Domainquality/, production/, dispatch/, costing/, packaging/ — the actual business rules, with no HTTP in them.
overrides/The doc_events hooks that attach those rules to ERPNext's own documents.

Mutating endpoints build ERPNext's own documents (make_stock_entry, make_purchase_receipt, make_delivery_note) and submit them. They never write a ledger directly, so every standard validation — and every Batchwell rule hung off it — runs exactly as it does in the Desk.

Genealogy is derived, never stored

The trace is computed from submitted stock transactions, Serial and Batch Bundle entries and Batch.parent_batch each time it is asked for. There is deliberately no genealogy table: a maintained graph can drift from the ledger, and a traceability answer that disagrees with stock is worse than no answer. Split batches produce multiple parents or children and are reported as such; cancelled and returned transactions are marked rather than dropped.

Idempotency

The three posting endpoints — receive_purchase_order, create_delivery_note and finish_production_run — take an optional request_id. A repeat of the same identifier returns the original document instead of posting again; a repeat with a different payload is rejected rather than silently treated as new. That is what makes a double-tap on a tablet safe.

The permission model

  • The console is a convenience over the same server rules, never a second route around them. The HTML shell carries no data; an anonymous visitor is redirected to login and a Website User is refused.
  • The company selector is a browser preference, not a trust boundary. Every endpoint re-checks permission, so choosing a company you cannot see returns nothing.
  • Recipe percentages are protected by permlevel 1, which Frappe applies to list views, document reads, reports, the export template and the exporter alike. Field-level security is not re-invented in the API layer.
  • FM roles grant nothing on standard ERPNext documents. That pairing is a provisioning decision, so refusals name the role to ask for rather than repeating the server's sentence about one DocType.

Asserted in tests/test_api.py: an inspector cannot release through the API, and finish_production_run still refuses an unreleased lot. If you add an endpoint, add the equivalent test — the point of the suite is that the HTTP surface cannot become a way around the rules.

The frontend

Vue 3, frappe-ui and Tailwind, with vue-router owning everything below /fm. {{ facts.screens }} routes plus a catch-all, because a mistyped link rendering an empty shell with no explanation is worse than a 404. 

cd apps/food_manufacturing/frontend
yarn install
yarn build     # writes ../food_manufacturing/public/frontend and www/fm.html
yarn dev       # Vite dev server, proxied to bench

Build output and the generated www/fm.html are gitignored — the repository holds sources only.

Boot data

The built shell writes each key of the boot context onto window, so www/fm.py must supply it. Without it window.csrf_token is never set, frappe-ui sends every request with no CSRF header, and Frappe rejects all of them — an app that loads perfectly and shows no data. get_csrf_token() only works inside a real HTTP session, so verify this over HTTP, never under bench execute.

The design harness

cd apps/food_manufacturing/frontend
yarn vite build --config vite.preview.config.js

It renders the real shell, router and pages with only @/data/api and @/data/session aliased to mocks, so what you see is what renders against a live site. It accepts query parameters a screenshot cannot otherwise reach — ?theme=, ?font=, ?deny for a permission refusal, and ?hover=<selector> to drive one pointer event for a tooltip. It is a development tool and is never served by the app.

Charts

Chart colours are computed, not chosen. Before changing any, run the data-visualization validator against this app's own card surface — not the reference surface — and keep the result in the commit message. The status order in the quality mix is deliberate: warning beside serious fails the normal-vision separation floor, so the series is emitted Released, Quarantine, Rejected, Hold to keep that pair apart.

Running the tests

{{ facts.tests }} tests across {{ facts.test_modules }} modules under food_manufacturing/tests/.

bench run-tests --app food_manufacturing discovers only one module on a v{{ facts.frappe_version }} site — it reports "Running 15 unspecified-category tests" and exits OK. The tests are fine; the discovery is not. Run them module by module to get the real total, and do not read a green --app run as a green suite. Tracked as point 3 in docs/BACKLOG.md. 

for f in apps/food_manufacturing/food_manufacturing/tests/test_*.py; do
  bench --site <site> run-tests --module \
    "food_manufacturing.tests.$(basename "$f" .py)"
done

The suite shares one long-lived site, which makes it order-dependent; a test that mutates a fixture must restore it in a finally. One known flake is recorded in the backlog rather than papered over.

House rules

What this repository is held to, and why each one exists.

  • Never edit Frappe or ERPNext core, and never globally restyle the Desk.
  • Business rules live on the server. Client code is for user experience, never for enforcement.
  • Never write stock or accounting ledgers directly, and never use a manual commit to hide a transaction problem.
  • Never invent a food-safety threshold. Every limit is configured per company. The app makes no certification or compliance claim anywhere, including in this handbook.
  • Never show a fabricated figure in a live screen, and label any isolated demo data explicitly. An unknown renders as an em dash, never as zero.
  • Hide or explain an unsupported feature rather than shipping a working-looking button that does nothing.
  • Report checks as PASS, FAIL or NOT RUN. Never claim a visual check without having looked at the screen, and never invent a successful test result.
  • Keep the documentation and the tests aligned with the code. This page is generated from the same repository; if it disagrees with the source, the page is the bug.

Known gaps live in docs/BACKLOG.md, ranked, each saying what "done" means. Deliberate omissions are listed there too, so nobody re-litigates them by accident.
